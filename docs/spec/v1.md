# pitwall v1 specification

This spec defines what pitwall v1 does, in enough detail to cut it into build tickets with no open decisions. Each section states current behaviour only. Where one decision replaced another, the later one is written here, and [section 19](#19-decisions-made-while-assembling-this-spec) lists what changed during assembly.

Terms follow `GLOSSARY.md`. Field names such as `m_sessionUID` are the game's. Decision history lives on the [wayfinder map](https://github.com/Vankata03/pitwall/issues/1) and its tickets; a **Source** line under a section names the tickets behind it.

An item marked **assumed** rests on a reference or a single sample and has not been confirmed on a capture. Section 18 lists how each one gets confirmed. Every limit in this document is a starting target until measured.

## 1. Product

pitwall is a second-screen race-engineer dashboard for the F1® 25 game, including the 2026 Season Pack. A single collector binary on the host receives the game's UDP telemetry and serves a tile-based web dashboard to any device on the LAN.

**Audiences.** The driver live, stream viewers, and demo audiences. Replay is therefore core to v1.

**Stack.** A clean-room Rust collector and a React + TypeScript dashboard, embedded in one binary. pits-n-giggles may be read for packet quirks, but no code is reused. MIT-licensed data may be used with attribution.

**Strategy is display only.** v1 shows stints, tyre age and wear, the game's pit window, gaps, rivals' tyres and stops, fuel delta and the weather forecast. It makes no predictions.

**Out of scope for v1.** Everything below stays out of this effort:

- an on-screen in-game HUD overlay
- strategy analysis, strategy suggestions, and an AI assistant or race engineer
- real-world F1 data (OpenF1, F1 Live Timing)
- formats `2024` and older, meaning F1 24 and F1 23
- persistent session history across sessions; the recording format leaves room for a later store to read recordings
- a 3D car model
- an installer and code signing
- a whole-field stint chart
- console support as a promise; it may work the same way, but it is untested
- transparent tiles, a single-tile URL, event jump and loop in replay, and compacting recordings to 20 Hz

**Source:** the map's Notes and Out of scope.

## 2. Collector deployment

### Packaging

v1 ships a portable, unsigned single binary for Windows x64 and macOS arm64, with the web assets, shipped track maps and fallback car embedded. There is no installer. The README and status page document the SmartScreen and Gatekeeper warnings.

Windows is primary because the game runs there. macOS must work but must not block v1. A collector on macOS sees live data only from a game on another machine and otherwise serves replay.

### Run surface

The Windows build is a tray app with no console window, and it writes logs to a file. macOS gets the same menu-bar app if one Rust tray library covers both without per-OS code; otherwise it runs in a terminal.

The tray menu holds:

- a state line (`Waiting for game` or `Receiving 60 Hz`)
- Open dashboard
- Show QR
- Settings
- Open log folder
- Quit

The app stays quiet except on first run, when it opens the browser. A second launch opens the existing dashboard and exits. If a port is taken, the app stays in the tray in an error state with a notification naming the port, so the user can fix it in Settings. Start with Windows is an opt-in setting, off by default.

### CLI and config

Defaults are UDP `20777` and HTTP `8777`, so pitwall needs no configuration once telemetry is on in the game. Settings live in a TOML file, which the status page edits and CLI flags override.

```toml
[udp]
port = 20777

[http]
port = 8777
bind = "0.0.0.0"

[forward]
enabled = false
targets = []            # "host:port" strings

[recording]
enabled = true
size_cap_gb = 20

[app]
start_with_windows = false
```

The flags are `--console` (terminal mode for debugging), `--udp-port`, `--http-port`, `--bind` and `--config <path>`.

UDP port and forwarding changes apply live. An HTTP port or bind address change restarts the listener and redirects the page. Settings warns first, because other screens drop until they get the new URL.

### Files

Everything lives in the OS per-user folder from day one, so a later installer needs no migration: `%APPDATA%\pitwall` on Windows and `~/Library/Application Support/pitwall` on macOS.

| Path | Contents |
| --- | --- |
| `config.toml` | Settings |
| `layouts.json` | The layout library |
| `recordings/` | `.pitrec` files and sidecars |
| `tracks/` | Cached track maps |
| `liveries/` | The optional livery pack |
| `logs/` | Log files |

### Finding the dashboard

The collector listens on all interfaces, so it needs no setting to tell the two setups apart: a game on the same PC sends to `127.0.0.1`, and a game elsewhere sends to the collector's LAN IP.

`http://<lan-ip>:<port>` and a QR code are the guaranteed paths. `pitwall.local` over mDNS is a best-effort extra. With several network adapters, the status page lists every candidate and the QR code uses the one holding the default route.

### Sharing telemetry

The game targets pitwall, and pitwall can forward raw packets unchanged to a configured list of `host:port` targets. Forwarding is off by default and sends live packets only. Broadcast mode is documented as an alternative, with no engineering behind it.

### LAN trust

Viewing is open over plain HTTP with no authentication. There are no tokens and no login.

Mutating HTTP requests must use `Content-Type: application/json`, carry an `Origin` matching `Host`, and name a `Host` that is a known address of this machine. This stops a web page in a browser on the host or LAN from driving the collector, including through DNS rebinding.

Host-only routes also require a loopback peer address. Layout editing is open to the LAN by design, unlike settings.

The status page explains the first-launch Windows Firewall prompt and Public-network blocking. Plain HTTP is not a secure context, so the Wake Lock API is unavailable; the docs explain how to disable Auto-Lock on iPad.

### Connection lifecycle

When the collector is unreachable, a screen notices that nothing has arrived, then reconnects forever with backoff and keeps the last values dimmed under an indicator. When the game is not sending, tiles stay in place in their empty state under a thin banner with a setup hint. The layout never disappears.

### Status page

The status page lives at `/status` and shows:

- connection state and measured packet rate
- the QR code and candidate URLs
- a first-run checklist for the game's settings
- live CPU, memory and latency percentiles
- dropped-packet, UID 0 and closed-UID counts
- format guidance (section 3)
- the name of any missing Stream view layout
- the recordings list
- the full notice (section 15)

On the host it also holds settings, Relearn map, replay start and stop, recording delete and pin, and Open recordings folder. Game-setup warnings appear here only, never on tiles.

**Source:** [How does the collector run and get found on the LAN?](https://github.com/Vankata03/pitwall/issues/7), [What goes over the wire from collector to dashboard?](https://github.com/Vankata03/pitwall/issues/9)

## 3. Telemetry ingest

### Required game settings

UDP on (it is off by default), UDP Format `2025` or `2026`, port `20777`, broadcast or the collector's IP, and a send rate of 20 to 60 Hz. The send rate is recommended at 60 Hz. The status page warns when the measured rate is below 60 Hz.

### Formats

The collector picks a parser per datagram from `m_packetFormat`. Both parsers feed one model sized for 24 cars with u16 team, driver and network IDs, and format differences stop at the parser. Layouts come from `docs/research/f1-25-udp-telemetry.md` on the `research/f1-25-udp-telemetry` branch for `2025`, and from `docs/research/f1-25-2026-udp-format.md` for `2026`. The `2026` layouts match the capture by size. Time Trial and Lobby Info are unchecked for `2026`.

| Situation | Behaviour |
| --- | --- |
| Unsupported format such as `2024` | Not parsed and not recorded. The status page names the format received and how to change it. |
| `2025` stream carrying the 2026 grid | Accepted. The status page hints to set UDP Format to `2026`. The detection rule comes from a build check; until then no hint shows. |
| Format change on one UID | Starts a new session, so each recording holds one format. |

### Regulations

A car counts as 2026 when `m_2026Regulations` says so, not because the stream uses format `2026`. Every car in a `2025` stream counts as pre-2026. Regulations are held per car.

### Packet rates

| Packets | Rate |
| --- | --- |
| Motion, Lap Data, Car Telemetry, Car Status, Motion Ex, Car Telemetry 2 | Menu rate, 20 to 60 Hz |
| Car Damage | 10 Hz, measured on one capture |
| Session, Car Setups | 2 Hz |
| Lap Positions | 1 Hz |
| Session History, Tyre Sets | Rotating, about 1 Hz per car |
| Participants | Every 5 s |
| Events | As they happen |

### Packet handling

Per packet type, a datagram not newer than the last applied `m_overallFrameIdentifier` is dropped, and a new session resets this. Loss is not repaired. Event packets always apply, in arrival order. The status page shows the dropped count. The recorder runs before this check, so a recording keeps every datagram of the session.

Two exemptions apply, because the results burst carries frame 0. Final Classification always applies. While a session is `ended`, Session History also applies. Everything else on that UID is ignored while `ended`. Exempting all frame 0 packets is wrong, because the flush just before `SEND` also carries frame 0 and could move state backwards.

### Game signals, from one capture

- A restart sends `SEND` on the old UID, then a new `m_sessionUID` about 3 seconds later, then `SSTA`, with frame and session time back at zero.
- Menus send UID 0 with frame 0.
- Before each `SEND`, 22 Session History packets arrive on UID 0 carrying the session's last frame number.
- About 23 seconds after a finished session's `SEND`, one burst arrives on the ended UID: 22 Session History packets and the Final Classification, with frame 0. The restarted session sent no burst. This timing is not a constant to rely on.
- The game can send nothing for over 30 seconds while paused.
- Nothing depends on `SSTA`, which is reported as unreliable.

## 4. Recording

### What is stored

A recording holds every datagram of one session with its arrival timestamp, plus a header. No processed state is stored, so collector fixes and new derived values apply to old recordings, and recordings can serve as test input. Compression is lossless and replay output is identical. Unused packets are never dropped.

### Session identity and boundaries

A session is identified by `(m_sessionUID, m_packetFormat)`.

- **Opening.** A recording opens on the first packet with a non-zero UID whose identity is not in the closed set.
- **Closing.** A recording closes at the first of: Final Classification, a new non-zero UID, a format change on the same UID, or collector exit. Silence never closes a recording, however long the pause, and the file resumes under the same UID. `SEND` only marks the session ended.
- **No classification.** If the game quits without a classification, the file stays open until the next session or exit.
- **UID 0.** These packets are never recorded and never reach the session model. Only connection status reads them, for game-reachable and format guidance, and the status page counts them.
- **Closed set.** The collector keeps an in-memory set of closed identities for the run. Their packets go to no file and no model, and the status page counts them. A recording is never reopened. The set is not persisted; the worst case after a collector restart is a tiny file that the 60-second rule deletes.

Recording is on by default, with a host setting to turn it off.

### `.pitrec` format

A `.pitrec` file is an append-only stream, little-endian:

| Part | Layout |
| --- | --- |
| File magic | 8 bytes, `PITREC` then u16 file version |
| Header | u32 byte length, then JSON: packet format, game version, pitwall version, recording start time (UTC) |
| Body | Repeated blocks of u32 compressed length, then one zstd frame |

Each zstd frame holds the records of about one second of arrival time, grouped by packet ID, which beats arrival order by about 9% under gzip on the one capture checked. A record is `u32 seq`, `u64 arrival_us`, `u16 length`, then the datagram. `seq` is the record's arrival position in the file, so a reader restores exact arrival order by merging on it. `arrival_us` counts from the first record.

A crash loses only the last unfinished frame, because a reader stops at the first incomplete block.

### File lifecycle

1. While open, a recording is `recordings/<uid>-<format>.pitrec.part`, written with fast zstd. Writes never block ingest.
2. On close, the collector drops the file if the arrival span of its records is under 60 seconds. Otherwise it renames the file to its final name, writes the sidecar and adds it to the list. The name needs the track and session type, which is why it is set at close.
3. It then recompresses at a high level, at low priority, to a temporary file and swaps it in atomically, so this never competes with the game. After that the `.pitrec` is immutable. The compression levels come from a build task.
4. A `.part` file found at startup was left by a crash. It goes through steps 2 and 3.

**Names** look like `2026-10-31_1430_Monza_Race.pitrec`, with a UID suffix only on a collision.

**Sidecar.** A `.json` beside each file holds track, session type, duration, lap count and the pinned flag. A missing sidecar is rebuilt by scanning the `.pitrec`. The status page lists recordings from sidecars. Files copied into the folder appear after a rescan.

**Retention.** A total size cap (default 20 GB, host setting) deletes the oldest recordings first. Pinned recordings and a recording currently loaded in replay are never deleted automatically.

**Size estimate.** A 45-minute race is about 1.15 GB raw and about 280 MB at the gzip ratio measured. The zstd figure comes from a build task; until then, size is a target.

**Privacy.** A `.pitrec` holds raw names, so sharing one shares them.

**Source:** [How are sessions recorded and replayed?](https://github.com/Vankata03/pitwall/issues/10), [How should recording find session boundaries?](https://github.com/Vankata03/pitwall/issues/17)

## 5. Session model

### Principle

The session model is a pure function of timestamped inputs. It reads no wall clock and no outside files, so replay, checkpoints and test recordings all produce the same result. It has two inputs: `apply(arrival_time, datagram)` and `advance(time)`. The second carries silence, because `lost` and `stale` must fire when nothing arrives. The live caller drives `advance` from the monotonic clock, and replay and tests drive it from recording time.

The live model always runs. Replay runs a second instance, and screens read whichever is active, so leaving replay returns to correct live state at once.

### Collector versus dashboard

The collector computes every car-level fact: gap to leader, laps behind, lap and sector bests, stint ages, pit stops, ERS %, and live delta against both references. The dashboard does only cheap relative arithmetic and presentation: the gap between two chosen cars (a subtraction of gaps to leader), units, and rendering of readout states.

Other derived rules:

- **ERS %** is `m_ersStoreEnergy` divided by 4 MJ. This capacity is **assumed**, and a build check confirms it on 2026 cars.
- **Fuel delta** is `m_fuelRemainingLaps` as sent.
- **Tyre condition** is 100 minus raw wear. Missing or restricted wear never appears as 100%.

### Depth per car

Every car, up to 24, keeps its laps, sectors, stints, pit stops and penalties for the whole session, because focus is per device and history must exist before anyone looks at it.

High-rate data is bounded. Each car keeps distance-bucketed samples for its current lap, its last two completed laps, and its best and former best. Screens are served only the current, previous and best laps. Older laps keep a summary. A completed lap's samples are immutable and shared by reference between checkpoints, so a checkpoint costs little more than the current laps.

### Session lifecycle

| State | Entered by | Effect |
| --- | --- | --- |
| `waiting` | Start, with no session seen | Tiles empty, setup hint shows |
| `live` | First packet of a session | Normal |
| `ended` | `SEND` or Final Classification | Only the exempt packets of section 3 apply |
| `lost` | 30 seconds of silence while `live` | Whole model stale, reads "No data: game paused or closed". Wipes nothing; the same UID resumes. |

The collector cannot tell a pause from a quit. The last session stays visible, including Final Classification, until the first packet of a new session wipes it. A restart is a new UID and a full reset. Sessions in a weekend share nothing in v1. The session time in Final Classification is stored as sent. The same code runs in replay.

### Flashbacks

Laps, sectors, stints, pit stops, penalties and distance samples after the flashback time are removed, and bests are recomputed. The race-control log keeps its rewound entries, marked `rewound`, and gains one flashback entry. Everything accumulated therefore carries a session time. The epoch bumps. Past the kept sample depth, delta is `absent` until a new reference forms.

### Stints and pit stops

The fitted tyres decide a stint, not a pit stop: drive-throughs, stop-gos and wing-only stops do not end one, and a red-flag tyre change does. Live stints come from Car Status. Session History stints overwrite them on arrival, because they are authoritative but about one second late. A starting age above zero marks a used set. Pit stops are separate entries.

### Cars and identity

- Vehicle index identifies a car within a session. A car is valid only if `m_resultStatus` is neither 0 nor 1.
- An empty slot reports team 65535, so `m_myTeam` alone identifies My Team.
- A retired car stays in the model until the session ends, frozen, with its status and `RTMT` reason. Focus and pins stay on it and show "retired", with no silent fallback.
- AI takeover keeps the same car and index.
- A pin survives across sessions by `driverId`. Online humans are pinned by name, because `networkId` is session-scoped.
- The player car is `m_spectatorCarIndex` while `m_isSpectating` is set, and `m_playerCarIndex` otherwise. A secondary player gets no special handling.

### Race-control log

One ordered log per session holds game events plus collector-derived entries. Each entry has a session time, lap, type, cars involved and source (game or derived). The derived set is flag changes, pit entry and exit, and weather changes. The model keeps everything and the race-control feed tile filters. Penalties appear in the log. Each car also holds current state from Lap Data (seconds, unserved drive-through and stop-go, warnings), which is authoritative for what is outstanding.

### Gaps

Race and sprint use the game's `m_deltaToRaceLeader*` and `m_deltaToCarInFront*`. The collector also computes laps behind for every car from race distance. Own timing points get built only if a capture shows lapped values are broken. Practice, qualifying and Time Trial use the difference to the session-best lap. A car with no time is `absent`.

### Restricted data

A car's `m_yourTelemetry` setting marks it as restricted. Its fuel, ERS, damage, wear and tyre sets are stored as restricted, never as zero, on entry to the model. Tyre temperatures, pressures, brake temperatures, engine temperature, tyre compound and age, DRS state, timing and positions are never restricted. Whether compound and age hold on a restricted car joins the build checks.

### Readout states

The collector decides the state per packet group per car. A group is `stale` after three of its expected intervals of silence, measured on arrival timestamps so replay matches. The whole model is `stale` while `lost`.

### Weather and pit window

Only the latest forecast is kept, with actual weather changes in the race-control log. The pit window is stored on the session and tied to the player car. On any other car it is `absent`, with no estimate.

## 6. Lap references and live delta

**References.** Every car has two, both from its own laps. **Best** is its fastest valid lap. **Previous** is its last completed lap of any kind, with invalid laps marked. Lap 1 and safety-car laps are eligible if valid. An invalid lap keeps its live delta running and shows its invalid mark, but can never become best. There is no session-fastest reference in v1.

**Lap completion.** The completed-lap delta appears at once, using `m_currentLapInvalid` as last seen on that lap. Session History arrives about a second later and overrides validity and best if it disagrees. The reference for a completed lap is the best available before that lap finished.

**Computation.** Reference time is stored per 5 m bucket of lap distance. Live delta is the current lap time minus the reference time at the same distance, linearly interpolated between buckets, with no smoothing. Negative means ahead. Samples with negative `m_lapDistance` are dropped. Delta keeps running through in-laps and out-laps, pit lane included. The bucket size may be recalibrated during the build if jitter shows.

**At the line.** The live figure is replaced by the official delta from lap times, never from samples. Sectors 1 and 2 come from Lap Data, and sector 3 is the lap time minus both.

**No reference.** Live delta is `absent` unless the named reference lap itself has samples. It never falls back to a different lap, so a best known only from Session History gives no live delta. Sector and completed-lap deltas still work from lap summaries. Gaps inside a reference lap are interpolated up to 100 m, and beyond that the stretch is `absent`.

**Focus and sessions.** The collector computes both deltas for all cars, so a focus change needs no recompute. A new session resets everything.

**Selection.** The reference is a per-tile setting stored in the layout, defaulting to best. A completed sector shows its time and signed delta against that same reference lap. The completed result stays on the tile until the first sector of the next lap completes.

**Time Trial.** Nothing is seeded, because the packet has lap and sector times but no distance samples. Best stays this session's laps. Personal best and rival appear as plain lap and sector times, and they are extra references for sector and completed-lap deltas, available in Time Trial only.

**Source:** [How do live delta and lap references behave?](https://github.com/Vankata03/pitwall/issues/16), [What should the dashboard look like?](https://github.com/Vankata03/pitwall/issues/6)

## 7. Track maps

The track store holds shipped and learned maps. It sits outside the session model and outside checkpoints. A map is keyed by `(trackId, trackLength)`. The telemetry format is not part of the key.

**Shipped set.** 22 layouts converted from windman007/f1-25-pit-wall, embedded read-only: Abu Dhabi, Austria, Baku, Brazil, Catalunya, Hungaroring, Imola, Jeddah, Losail, Melbourne, Mexico, Monaco, Montreal, Monza, Sakhir, Shanghai, Silverstone, Singapore, Spa, Suzuka, Texas and Zandvoort. Points are game world X/Z, indexed by lap distance at about 8 m. Only the track ID, track length and points are imported. The source's `corners` data comes from the MultiViewer API, which carries no licence, and must not be imported. No pit lanes ship.

**Learned layouts.** Las Vegas, Miami, the three reverse layouts, Madrid and anything unknown.

**Lookup.** Cached file, then shipped map, then learn.

**Learning.** Live and replay can both feed the learner, and the first complete map wins. The learner buckets every valid car's X/Z (Y is vertical) by `m_lapDistance` at 8 m. A sample is rejected when the car is in the pit lane (`m_pitStatus` non-zero), when the lap is invalid, or when lap distance is negative. A map is complete when every stretch of the lap is covered, with no gap over 40 m.

The promise is one clean lap of coverage, not a lap count. A race with AI cars fills the map during lap 1, and a solo Time Trial needs one clean lap. Rejected samples can force a second lap.

**Sectors and start.** Start/finish sits at 0. Sector boundaries come from `m_sector2LapDistanceStart` and `m_sector3LapDistanceStart`, so nothing per-track is stored.

**Cached files.** One file per map at `tracks/<trackId>-<trackLength>.json`, holding the outline, pit trace and a schema version, written as soon as the map completes. There is no manifest. An unreadable or old-schema file is ignored and relearned. The owner may copy these files between hosts. They never enter the repository or the binary.

**Freezing.** A complete map stops changing, and shipped maps count as complete. If live cars sit far off the stored line across one full lap, a new cached map is learned in its place. The shipped copy is never altered. The threshold comes from a build task. The host-only Relearn map action drops the cached file and falls back to the shipped map if there is one.

**Pit lane.** Completeness ignores the pit lane. A pit trace is added the first time a car drives the whole lane, then freezes the same way. Partial passes are discarded. A pit lane learned on a shipped map is saved in a cached file on top of it.

**Tile while learning.** The line grows as samples arrive under a small "Learning map" label. Car dots come from raw X/Z from the first sample. The tile refits in steps as bounds widen, not per frame, and a sector marker appears once there is line under its lap distance.

**Source:** [How do shipped track maps get built?](https://github.com/Vankata03/pitwall/issues/23), [How do we get track map outlines and sector markers?](https://github.com/Vankata03/pitwall/issues/4)

## 8. Wire protocol

Each screen holds one WebSocket at `/ws`, carrying everything from collector to dashboard. Requests from the dashboard go over HTTP. A command's result comes back through the stream, so every screen sees the same state. The binary always ships its own dashboard, so there is no version negotiation and the wire can change in any release.

### Data classes

| Class | Contents | Rule | Encoding |
| --- | --- | --- | --- |
| Frame | Bounded per-car values at game rate | Sent whole, no deltas | Binary message |
| State | Bounded current values for session, cars and collector | Sent whole at 5 Hz; a skipped update is repaired by the next | JSON text |
| History | Laps, stints, pit stops, penalties, race-control log | Snapshot on connect, then appends, sent immediately | JSON text |

### Epoch

Any change that an append cannot express bumps the epoch: a flashback, a new session, a replay seek, or a switch between live and replay. A screen then discards everything and receives a fresh snapshot, so flashback logic lives only in the collector and the wire has no removal messages.

Every History entry has a stable `id`. An appended entry whose `id` already exists replaces that entry. This carries corrections from Session History, such as a lap's validity or a stint's final figures, without an epoch reset.

### Text messages

| `type` | Fields |
| --- | --- |
| `hello` | `buildId`, `epoch`, `source` (`live` or `replay`). First message on connect. |
| `snapshot` | `epoch`, `source`, `state`, `history`. Follows `hello`, and follows any epoch bump. |
| `state` | `epoch`, then the State fields |
| `history` | `epoch`, `entries` (each with `kind`, `id`, and its body) |

On a build ID mismatch the screen reloads itself, or shows a reload prompt while in edit mode so unsaved edits survive. A screen drops any message from an older epoch.

### Frame layout

A Frame is a 16-byte header followed by 24 fixed 40-byte car entries, little-endian, 976 bytes in all. It creates no per-frame objects: the dashboard reads it with `DataView` into typed arrays. One field table in Rust defines this layout and generates the TypeScript decoder.

Header: `u32 epoch`, `u32 seq`, `f64 sessionTime`.

| Offset | Field | Type | Unit |
| --- | --- | --- | --- |
| 0 | speed | u16 | km/h |
| 2 | gear | i8 | -1 R, 0 N |
| 3 | throttle | u8 | % |
| 4 | brake | u8 | % |
| 5 | steering | i8 | -100 to 100 |
| 6 | rpm | u16 | |
| 8 | worldX | f32 | m |
| 12 | worldZ | f32 | m |
| 16 | lapDistance | f32 | m |
| 20 | currentLapTime | u32 | ms |
| 24 | deltaBest | i32 | ms |
| 28 | deltaPrevious | i32 | ms |
| 32 | gLateral | i16 | G ÷ 1000 |
| 34 | gLongitudinal | i16 | G ÷ 1000 |
| 36 | ersPercent | u8 | % |
| 37 | aeroState | u8 | DRS or active aero state |
| 38 | readout | u16 | 2 bits per group |

The `readout` bits, in order from bit 0, are telemetry, motion, lap, status, delta best, delta previous and aero, each `0` live, `1` stale, `2` restricted or `3` absent. Bits 14 and 15 are reserved. Empty car slots read `absent` throughout.

A later field goes in Frame only if a tile redraws visibly faster than 5 Hz. Everything else goes in State.

### Rates and traffic

Every car goes to every screen at full rate, with no focus reporting and no per-screen state in the collector, so a focus switch is instant. Traffic is about 59 kB/s per screen at 60 Hz.

A fixed 60 Hz timer outside the session model sends Frame when values have changed, so the model stays pure. It adds up to about 16 ms of delay, and it behaves the same at any game send rate and replay speed: a 20 Hz game gives 20 Frames per second, and 4x replay still puts 60 on the wire. A build task tries sending at the end of the game's datagram burst instead.

### Backpressure

Each screen has a bounded send queue. Frame and State keep only the latest value. History and snapshots are never dropped. If a screen's History queue passes 4096 entries, the collector closes that connection, and the screen reconnects under its existing backoff and gets a fresh snapshot. A slow screen never delays other screens or game ingest.

### State contents

State carries:

- session facts: track, session type, lifecycle, weather and forecast, pit window, safety car status
- the player car
- per-car facts: participants, regulations, tyres, brakes, pressures, engine temperature, fuel, damage, gaps, laps behind, tower data, overtake and boost, and harvest limit
- per-group readout state outside Frame
- status-page data: packet rate, dropped count, format warnings
- replay mode with position, speed, banner, load progress and the background live session notice
- revision counters for the layout library and track map

Focus car is not on the wire. A counter change makes screens refetch over HTTP, so a saved layout reaches other screens within about 200 ms.

### Lap traces

Current, previous and best lap samples are fetched per car and lap, on demand, as columnar JSON at 5 m buckets: time, speed, throttle, brake. A screen builds the current lap from Frame, and a lap-complete History entry tells it to fetch a new previous or best lap. A late joiner fetches the current lap so far. A reply from an older epoch is dropped.

### Types

JSON types are generated from Rust structs with `ts-rs`. CI regenerates both contracts, JSON and Frame, and fails on any difference.

## 9. Replay

Replay plays a recording through the collector as if the game were sending it. It replaces live for the whole collector, so all screens see the same replay under a banner. Live packets keep recording in the background. Replay is never re-recorded and never forwarded.

**Controls.** Pause, speed (0.5x, 1x, 2x, 4x), a seek bar and lap jump work from any screen. Start, stop, delete and pin are host-only, so nobody on the LAN can knock the driver out of the live view, while an iPad can still drive a demo the host has started.

**Load and seek.** On load, the collector runs the whole recording through a model instance at full speed, with a progress bar, holding in-memory checkpoints every 30 seconds plus a lap index. A seek restores the nearest checkpoint and fast-forwards. Nothing is persisted, so model changes stay safe.

**Time.** Replay runs on arrival time, so a flashback plays exactly as it did live, and silence plays as recorded. The seek bar is wall-clock time, not game time. A lap can exist twice, and lap jump targets the last attempt.

**Edges.** At end of file, replay pauses on the last frame with a banner offering restart or exit. If the game starts sending during replay, a banner says a live session is recording in the background, with no auto-switch.

**Moving recordings.** Copy `.pitrec` files into the folder. There is no browser upload and no sample recording in the binary.

**Source:** [How are sessions recorded and replayed?](https://github.com/Vankata03/pitwall/issues/10)

## 10. Dashboard

### Stack

React 19 with TypeScript. react-grid-layout pinned at 2.2.4 until the 2.3.0 drag/resize regression (#2303) is fixed, with gridstack.js as the fallback. uPlot for traces. No WebGL, and ECharts and visx stay off the 60 Hz path.

The dashboard must run on Chromium 127, for OBS.

### Rendering

60 Hz data stays out of React state. WebSocket messages write into mutable stores and ring buffers. One shared `requestAnimationFrame` loop calls `draw()` only on tiles whose data changed, using the frame timestamp. Traces, the track map and gauges draw with Canvas 2D, and small numbers are written straight into the DOM. Slow data reaches React through `useSyncExternalStore` at 4 to 10 Hz. Each frame shows the latest value with no interpolation, and 120 Hz screens get no special handling.

### Tile contract

Each catalogue entry is one tile type, and a layout can hold several tiles of a type, each with its own settings. A tile type declares:

- **Car binding:** `follows-car` or `session-wide`. A `follows-car` tile is set to Focus (default), Pinned driver, Car ahead or Car behind. A pinned car not in the session shows "car not in session" and keeps the pin.
- **Sizes:** a minimum and default size, plus two or three named densities (compact, regular, full) chosen from the tile's actual size. There is no maximum, and content is never scaled with CSS.
- **Data:** a typed list of what it reads, plus a rate class. `frame` tiles run at 60 Hz through `draw()`, and `slow` tiles at 4 to 10 Hz. The declaration lives on the dashboard side. It drives the dirty check, the missing-data states and availability hints in the add-tile picker, and it does not filter wire traffic.

### Missing data

Each readout is in one of four states:

| State | Meaning | Display |
| --- | --- | --- |
| `live` | Current | Value |
| `stale` | No recent data | Dimmed last value with a marker |
| `restricted` | Withheld by the game | Label |
| `absent` | No value yet | Em dash |

A tile keeps its shape, nothing reflows, and zero never stands in for a missing value. A whole-tile message appears only when no readout has data.

### Layouts

Layouts live in one shared library in `layouts.json` on the host. Names are unique. Each device remembers only which layout it shows, in browser storage. Losing that memory costs one re-pick.

A layout holds a schema version, its name, and one arrangement per screen class, each a list of tiles with `{i, type, x, y, w, h, settings}`. Tile settings belong to the tile instance. An unknown tile type or setting renders as a placeholder, and its data is kept.

**Grid.**

| Screen class | Width (CSS px) | Columns |
| --- | --- | --- |
| Wide | 1280 and up | 24 |
| Tablet | 768 to 1279 | 12 |
| Phone | Below 768 | 4 |

Row height is 32 px with an 8 px margin, and the page scrolls vertically if a layout is taller than the screen. A class nobody has arranged is generated from wide until it is edited.

**Choosing.** A new device opens Pitwall Classic. Every screen has a layout switcher, which also renames, duplicates and deletes. Presets cannot be deleted. Deleting or renaming a layout on another screen moves screens showing it to Pitwall Classic with a notice. `?layout=<name>` opens a fixed layout without device memory.

**Several screens.** Screens viewing a layout update live when it is saved. If two screens edit the same layout, the last Done replaces the whole layout with no merging or locking, and the other editor sees a notice.

### Edit mode

Edit mode is entered with an explicit Edit button, never a long press, so a touch during a race cannot move tiles. Tiles stay live, with drag handles and a settings control overlaid. It supports add, remove, drag, resize and tile settings, and ends with Done or Cancel. There is no undo stack in v1. The edit changes only the current screen class. Presets are read-only, so the first change makes a copy ("Pitwall Classic copy").

### Chrome

Every screen outside Stream view has a layout switcher, a focus-car picker, a display menu, an Edit button, a status page link, connection banners, and the short line (section 15).

**Focus car** is per device and stored in browser storage, using the same identity rule as a pin. Default focus follows the player car. The picker lists every car and has Follow player. A focus car absent from a new session shows "car not in session" until the viewer chooses again.

### Units

Three independent per-device selectors sit in the display menu, stored in browser storage. A new device starts on the defaults and does not follow the game's own preference.

| Quantity | Choices | Default |
| --- | --- | --- |
| Speed | km/h, mph | km/h |
| Temperature | °C, °F | °C |
| Pressure | psi, bar | psi |

Distance follows speed: metres with km/h, feet with mph. Fuel stays in kg and laps.

### Visual language

The accepted reference is the [Pitwall Classic prototype](../prototypes/dashboard-display-lab.html) ([screenshot](../prototypes/favourite-accepted-preview.png)). It is a visual reference, not production code, and all its readings and temperature ranges are simulated.

The dashboard is a dense charcoal instrument face with restrained borders, a central rendered focus car, calibrated gauges and wheel-local readouts, with papaya accents, teal energy and input traces, and a clear numeric hierarchy. The display font is Oxanium (OFL). Pitwall Classic uses the shift strip, thermal columns, battery segments, delta-first timing, meters plus combined trace, field overview, numeric weather, fuel delta and completed stint blocks.

The front-facing car view places the front axle below the rear axle and the driver's left on the image's right. Readouts stay tied to those positions.

| Temperature hot | `#FF9C35` |

**Temperature bands.** pitwall ships a fixed table, tyres keyed by actual compound and one table for brakes, and it is not user-configurable. Values come from a build task. If the compound is unknown, the readout shows its number without band colour.

### Non-colour cues

No meaning is conveyed by colour alone.

- Deltas carry `+` or `−`.
- Sector colours keep the F1 convention, plus a marker on session-best and personal-best.
- Flags show a letter or word (`SC`, `VSC`, `Y`, `R`).
- Cold and hot show an arrow glyph beside the number.
- Tyre condition shows a number and bar length, and colour only repeats them.

### Accessibility

- **Text:** at least 11px for labels and 14px for values at all densities. A tile that cannot fit drops readouts by density and never shrinks text. The prototype's 7 to 9px text is rework, not reference.
- **Contrast:** WCAG AA, 4.5:1 for text and 3:1 for graphics and meter fills, including `stale` values.
- **Keyboard:** tile arrangement is pointer-only in v1, a stated known gap. Everything else is keyboard reachable with visible focus: layout switcher, display menu, focus car, Edit, Done/Cancel and tile settings.
- **Touch:** targets are at least 44px.
- **Screen readers:** canvas tiles expose the tile name and a summary, with no live announcements at 60 Hz.
- **Motion:** nothing flashes above 3 Hz, including the shift strip at the limiter, which uses a steady fill. `prefers-reduced-motion` turns off decorative transitions, while live data still updates.

### Stream view

Stream view is a state of one screen, not a property of a layout: `?layout=<name>&stream=1`.

- **Chrome.** Tiles only. Everything in the chrome is hidden, including banners and the slow-draw notice. The Notice tile carries the short line.
- **Transparency.** The page background is transparent. Tile backgrounds stay opaque, so the game shows through the grid gaps.
- **Size.** The OBS source size is the viewport in CSS pixels, and the width rule picks the screen class. `&class=<wide|tablet|phone>` forces an arrangement. The layout must fill the viewport without scrolling, so row height here is the viewport height divided by the arrangement's rows. 1920×1080 is the documented starting size.
- **Single tile.** A one-tile layout gives this result, and density follows tile size.
- **Units.** `&speed=`, `&temp=` and `&pressure=` override the device value and need no storage.
- **Focus.** There is no focus parameter. Stream view follows the player car. A fixed driver is set with Pinned driver in the layout.
- **Failure on air.** Readout states still apply and reconnection is unchanged. Tiles never disappear when data stops.
- **Missing layout.** If the named layout is missing at load, or is deleted or renamed while open, the page renders nothing but its transparent background. The collector logs it and the status page names it. This overrides the Pitwall Classic fallback for Stream view only.
- **OBS.** OBS Studio's current and previous major versions are supported. An OBS source counts as one of the 4 guaranteed screens. There is no 60 fps promise inside OBS. The docs tell streamers to enable the source's custom frame rate at 60, which is off by default.

### Live delta

`live-delta` is a follows-car, frame-rate tile with a huge signed headline and a graph of the delta around the lap. Minimum size is 6×3 and default 12×6.

**Headline.** The delta in seconds to three decimals with a real minus sign (`+0.123`, `−0.123`), green (`#7ED99C`, sector personal best) when ahead and amber (`#F2D14B`, sector slower) when behind. Zero takes the plain text colour. Every accepted Frame writes it straight into the DOM from the shared animation loop, with no React state and no smoothing. The four readout states apply: stale dims the last value with the marker, restricted shows the label (at a smaller size, so the word fits), and absent shows an em dash. A whole-tile message appears only when the collector or the game is the reason there is no value, because on a first lap there is no reference and absent is normal. The headline stays huge at every density: its font size is computed in pixels from the tile box and is never below 36 px. A wide box puts the headline beside the graph and a narrower one puts it above; Compact shows the headline alone.

**Graph.** Regular and Full add a Canvas 2D graph of delta against lap distance over the whole lap. The x axis runs from 0 to the track length from State. The y axis is symmetric about a zero line and rescales in 1/2/5 steps, with a floor of ±0.1 s. Ahead is drawn above the zero line and behind below it, labelled "ahead" and "behind" so the sign never rests on colour alone. The line is thick and continuous, with the area between it and zero filled, each half in its palette colour. Faint markers show the sector boundaries when State has them. A dot marks the car. A graph that would be under 60 px tall is left out rather than squashed.

**Samples.** Every accepted Frame appends `deltaBest`, `deltaPrevious` and `lapDistance` to the followed car's aligned rings, in Frame order and not per animation frame. The tile reads whatever the rings gained since its last paint, so Frames that arrive between two paints all reach the graph, and keeps the whole lap even though the rings hold only ten seconds. Gaps up to 100 m are joined with a straight line, a longer gap or a missing value breaks the line, and a hole left by an overflow (a hidden tab, for instance) breaks it too. A time that goes backwards starts the graph over. Crossing the line starts a new graph and keeps the finished lap, faint, ahead of the car until the new lap passes it. The official delta that the game's first Lap Data of a new lap carries (section 6) shows in the headline but is not plotted on either lap. Changing the car or reference, or an epoch change, resets the graph.

**Reference.** A per-tile setting stored in the layout: best (default) or previous, from `deltaBest` or `deltaPrevious`.

**Update rate.** The tile draws on every animation frame in which a Frame arrived, up to 60 per second, and nothing in the path from Lap Data to the DOM throttles that: the model applies each datagram on arrival, the collector sends a Frame every 1/60 s whose bytes changed, and the dashboard decodes each Frame into its stores when it arrives. The delta itself can change only when the game sends Lap Data, which is the menu rate of 20 to 60 Hz (section 3), so a 20 Hz game gives 20 new values a second however fast the screen draws. Any Frame in between repeats the last delta.

### Car status details

Readouts sit in fixed positions around the car, and art defines no anchors and never implies a value. Tyres show thermal columns and remaining condition, a primary readout that starts at 100% and decreases. Damage is numeric. Compact density drops the car and keeps the readouts.

### Timing tower

The tower highlights the focus car's row and never scrolls. Columns are fixed by density, with no toggling or reordering:

| Density | Columns |
| --- | --- |
| Compact | Position, driver, gap, compound |
| Regular | Adds team colour, tyre age, stops, status |
| Full | Adds last lap, best lap, penalties with track-limit warnings, tyre wear, positions gained or lost |

Compound shows the visual compound. ERS, fuel, damage and speed trap stay out of the tower.

**Rows.** A setting chooses Full field or Around focus (±N cars, default 3). Compact defaults to Around focus with the leader's row pinned. Regular and full default to Full field and fall back to Around focus when rows do not fit.

**Race gaps.** A setting chooses Interval (default), Leader or Focus-relative, which is the difference between two gaps to leader. When two compared cars differ by a full lap or more, any mode shows `+N LAP` instead of a time.

**Other sessions.** Practice and qualifying order rows by the game's position. Row one shows its best lap. Interval and Leader show delta to session best. Focus-relative shows delta to the focus car's best, falling back to session best until that car sets a lap, and the column label names the reference. No lap set shows an em dash. Sector colours stay out of the tower. Time Trial shows a whole-tile message, because only the player runs.

**Race status.** Order and gaps stay live under safety car, VSC, red flag and formation. One band at the top names the status, from `m_safetyCarStatus` and events. Rows do not change style and gaps are not hidden.

**Row states.** In the pit lane a row shows PIT and keeps its gap. Retired and disqualified cars show status text, sink to the bottom, dim and stay in the list. When `m_showOnlineNames` is `0`, the row shows `#<race number>` instead of `m_name`, because `m_name` may hold a Steam ID.

### Stint tile

It shows completed and current stint blocks (compound, laps, tyre age, and wear when available) and stops. The pit window appears only when bound to the player car; otherwise it is `absent`. On a restricted car the blocks stay and wear shows `restricted`. Rivals' current tyres and stops live in the tower, and there is no separate rival table.

## 13. Liveries

Liveries come from two sources: a local livery pack of real car images on the host, and one original fallback car that ships with pitwall.

**Art rule.** No pack image ever enters the repository or the binary, whether or not the repository is private. pitwall never bundles, downloads or hot-links real art. Streaming and demos with real art stay at the owner's own risk. README images and official demo footage use the fallback car.

**Pack contract.** A pack is a set of images in `liveries/` on the host. Each is a transparent PNG, 4:3 at 960×720, with shared car framing and the front-facing view. There is one image per team, named `<teamId>.png`, plus `my-team.png`, chosen by `m_myTeam`. There is no manifest. A file that matches nothing is ignored, and a car with no file uses the fallback. Team IDs do not collide between grids, so `0`–`9` and `476`–`486` share one flat folder.

**Fallback.** One original neutral car, recoloured with the livery colours, with one body for both regulations.

**Colours.** Game colours come first: `m_numColours` and the four RGB livery colours in Participants. A shipped team palette is added only if a build check shows those colours are unreliable. Neutral is the last resort.

**Race numbers.** Images are per team, so the number on a car may belong to the teammate. This is accepted as cosmetic.

**The owner's pack.** A 21-car pack sits outside the repository at `~/Desktop/Projects/pitwall-livery-pack/`, covering the 10 teams of the 2025 grid and the 11 of the 2026 grid. The 2026 ID order comes from the pits-n-giggles team table, not EA's appendix.

**Source:** [How do liveries work?](https://github.com/Vankata03/pitwall/issues/12), [Where can real-livery car art come from, and what may we do with it?](https://github.com/Vankata03/pitwall/issues/3)

## 16. Performance budget

**Load.** v1 guarantees 4 simultaneous screens at full rate. Further screens are accepted with no guarantee.

**Devices.** Phones and tablets released in the last 5 years, on the current or previous major version of Safari, Chrome, Edge or Firefox, plus OBS (section 10). Tablets and desktops are promised 60 fps. Phones are promised 30 fps, with 60 fps as the target.

| Measure | Limit | If missed |
| --- | --- | --- |
| Datagram arrival to draw commit, 5 GHz Wi-Fi with the screen in the same room | p95 ≤ 50 ms, p99 ≤ 100 ms | Blocks release |
| Datagrams dropped by the collector | 0 | Blocks release |
| Collector CPU | ≤ 25% of one logical core, sustained | Soft |
| Collector memory | ≤ 256 MB RSS, replay checkpoints included | Soft |
| All tile `draw()` calls together | ≤ 8 ms per animation frame, lowest supported device, densest shipped preset | Limit for tile authors |
| Epoch reset to redrawn tiles | ≤ 500 ms | Soft |
| New connection to drawn tiles | ≤ 2 s | Soft |
| Replay seek | ≤ 1 s | Soft until calibrated |
| Load of a 2-hour recording | ≤ 10 s | Soft until calibrated |

A soft limit may be widened on evidence, and any widening is recorded here. Display scanout is excluded from latency.

**Worst case.** The budgets apply to live plus 4x replay, 4 screens and recording on, including one model instance each for live and replay. A 3-hour endurance run must keep screen and collector memory flat after the first lap, History growth excepted. There is no per-tile drawing limit, so a heavy track map can be balanced by simple tiles. User-built layouts beyond the densest preset are not guaranteed.

**When a screen cannot keep up.** It always draws the latest value and drops frames. When its draw rate stays under 24 fps for 5 s, it shows a quiet, non-flashing notice in the display menu. Data and layout are never reduced automatically.

**Measurement.** Each release check replays the densest recording on the oldest device at hand with 4 screens, using the UDP re-send tool at 1x with recording on. That is evidence, not proof for the whole supported range.

**Source:** [What is the v1 performance budget?](https://github.com/Vankata03/pitwall/issues/19)

## 17. Testing

**Golden recordings.** A golden is a `.pitrec` file, so tests exercise the real reader. Only AI-field sessions may become goldens, so no other player's name reaches a file that could turn public. Pack art is never involved, and tests use the fallback car.

**Where they live.** Short clips under about 1 MB each are committed, so `cargo test` works offline. Full sessions and their `.pwcap` originals are assets on a dedicated `goldens` GitHub Release, pinned by SHA-256 in a checked-in manifest and cached by CI. The only golden today is `2026-spa-practice`.

**What blocks merge.**

- **Model:** approved, readable snapshots at each lap end, plus a hash of the whole run.
- **Wire:** Frame, State and History snapshots at fixed times, plus epoch behaviour, on a virtual clock driven by recording timestamps.
- **Replay:** seeking to a point gives the same state as playing straight through.
- **Contract:** the `ts-rs` and Frame table regeneration check.
- **Browser smoke test:** each preset loaded in pinned headless Chromium at a few seek points shows no tile errors. Screenshots are CI artifacts and are not compared.

A snapshot change needs explicit approval in the PR diff. Tile logic is tested from recorded wire data across all four readout states.

**Recorder tests.** A `.pitrec` holds one session after UID filtering, so boundary rules use a test-only input of timestamped raw datagrams across sessions and check the `.pitrec` files and sidecars that come out. The input is cut from the Spa `.pwcap` if it contains the restart, and is otherwise synthetic and labelled `assumed`.

**Platforms.** Windows runs on every PR, and macOS on `main` merges only. Both share one set of snapshots, so any platform difference is a bug.

**No capture yet.** Flashback, format `2025`, My Team, mixed grid and format, lapped-car deltas, spectating, restricted online cars and a full race are unobserved. Model unit tests cover them with small synthetic datagrams built from the packet tables, each labelled `assumed` until a real capture confirms it.

**Format versions.** Before the first release, `.pitrec` may change freely and goldens are regenerated from the `.pwcap` originals. After it, the reader supports every released version, and one frozen `.pitrec` per released version stays as a read test.

**Ingest benchmark.** It runs on the full Spa golden and compares the base commit and the change on the same runner, on Windows. It runs on `main` merges and on PRs labelled `perf`, and fails at 25% slower.

**Source:** [How does v1 get tested on recordings?](https://github.com/Vankata03/pitwall/issues/20)

## 19. Decisions made while assembling this spec

The tickets left these gaps or contradictions. Each was settled here, and any of them can be changed by editing this section and the one it names. None has been reviewed by the owner.

### Contradictions between tickets

1. **Frame traffic.** The wire and performance tickets give about 115 kB/s per screen, but 40 bytes × 24 cars × 60 Hz is 57.6 kB/s. This spec uses the correct figure, about 59 kB/s with the header. The budget is unaffected.
2. **History corrections.** History is append-only and any other change bumps the epoch, yet Session History overrides stints, validity and best about a second later. That would reset every screen whenever the two disagree. Section 8 lets an append replace an entry with the same `id`.
3. **Format change on a UID.** The format ticket starts a new session, but the boundary ticket's close list omits this and its closed set would then drop the rest of that UID. Section 4 identifies a session by UID and format together.
4. **Silence in a pure model.** `lost` and `stale` need time to pass with no datagram, which a function of datagrams alone cannot see. Section 5 adds an `advance(time)` input.
5. **Grouped records and arrival order.** Grouping by packet type would lose exact arrival order, which replay needs. Section 4 adds `seq` to each record.
6. **Recording names.** A file opens before the track and session type are known. Section 4 uses a `.part` file and names it at close.
7. **Checkpoint memory.** Full copies of per-car samples every 30 seconds would break the 256 MB limit on a long recording. Section 5 shares completed laps by reference.

### Replaced wording, for readers of older tickets

- Format warnings cover "unsupported or mismatched", not "not 2025".
- Layouts live in a shared library, not per device.
- The 30-second recording timeout and `SEND` as a close are gone.
- Shipped maps come from windman007, not from our own recordings.
- The track store key is `(trackId, trackLength)`, not track ID alone.
- Each car keeps the deeper sample set of section 5.
- Temperature ribbons became thermal columns.

### Palette check

The dashboard ticket required a simulation check before the palette entered this spec. Each set in section 10 was tested with Machado (2009) severity 1.0 protan, deutan and tritan matrices on the tile background.

- **Contrast:** the lowest text colour is the brake trace at 5.26:1, and the others reach 6.43:1 or more.
- **Separation:** every pair within a set stays at least ΔE76 26 apart under all three simulations. The tightest are condition healthy against mid at 26 in every case, sector session best against slower at 29 under tritan, and the throttle and brake traces at 31 under protan.

These results are computed. No person with a colour vision deficiency has reviewed them.
